# Phase 1 scope — get in, and stay in

> **If you are picking this work up, read [PHASE1-HANDOFF.md](PHASE1-HANDOFF.md) first.**
> That is the short, current summary: what exists, what is proven, what is broken, how to
> build and run it, the traps that will otherwise cost you hours, and the next steps in
> order. This document is the long-form record — how each conclusion was reached, and
> where the reasoning went wrong. §6 is the investigation log.

This is the working document for [IMPLEMENTATION-PLAN.md](IMPLEMENTATION-PLAN.md) Phase 1. It fixes
the decisions the plan leaves open, records what was verified before any code was written, and states
what each spike must prove. **It is written before the implementation, and updated as the spikes
answer their questions** — a scope document that only ever agrees with the code is not evidence.

The plan's Phase 1 has three spikes and one deliverable:

| | must prove | state |
|---|---|---|
| **Spike 1.1** | native code is resident before the game's `Main`, and says so in a log that predates the game's own | **confirmed live** |
| **Spike 1.2** | the JIT detour installs, and all four targets appear in the compilation stream matched by IL hash | **confirmed live** |
| **Spike 1.3** | one target can be patched and read live state at ~60 Hz for a long session without harm | **the patch and the live read are both confirmed live; the long session is not** |
| **Deliverable** | the hook skeleton: self-checks, the Phase 0 target table with a hard refusal, the offset-resolution pass, and an off switch | **built; the offset cross-check runs live and its verdict is published — offline for both outcomes** |

"Built" here means the code exists, compiles with warnings-as-errors, and passes every check that can
be made without a running game. It does **not** mean the spike succeeded.

**THE LIVE READ HAS SINCE HAPPENED — this paragraph said the opposite until 2026-10-11.** The
managed frame callback *was* disabled at attach, which is what left the read unproven here; arming
became a later decision made by a watcher-thread probe, the read itself became native, and two live
runs have now read `Player.Position` from the real game (`ARMED`, 232 and 223 successful reads,
`PASS 9c`). [PHASE1-VERIFICATION.md](PHASE1-VERIFICATION.md) is the current state; §6 of this
document is the record of how it was reached and is correct about everything except the read.

**The design frame rate is 60 Hz.** The game runs its frame loop uncapped — measured at roughly
200 Hz (~4.9 ms/frame) at the title screen — but Phase 1's budget and success test are written
against 60 Hz (16.7 ms/frame), the operator caps FPS in the game's own settings, and the high-rate
limit test is deferred. See [HOOK-ARCHITECTURE.md](HOOK-ARCHITECTURE.md) §7.

## 1. What was verified before writing code

### 1.1 `getMethodDefFromMethod`: the generated header says one slot, the runtime says another

[HOOK-ARCHITECTURE.md](HOOK-ARCHITECTURE.md) §4.3 requires this slot index to be confirmed rather than
assumed, and flags two conflicting community values (`0x76` from MonoMod's generated header, `105`
from xoofx/ManagedJit).

The authoritative *ordering* is the runtime's own autogenerated
`src/coreclr/inc/icorjitinfoimpl_generated.h`, whose header states it is *"in exactly the same order,
with exactly the same whitespace, as the ICorJitInfo interface declaration (with the `virtual` and
`= 0` syntax removed)"* — which is precisely the property a vtable index depends on. Flattening
`ICorJitCompiler` (4 slots) followed by that file's 174 declarations gives **178 slots**:

| slot | method (per the generated header) |
|---|---|
| `0x00` | `compileMethod` — confirmed by behaviour, unchanged on every .NET version |
| `0x02` | `getVersionIdentifier` — confirmed by behaviour; this is the GUID check |
| `0x62` | `getFieldOffset` |
| `0x67` | `isFieldStatic` |
| `0x7A` | `getMethodDefFromMethod` |
| `0x33` | `getStaticBaseAddress` |
| `0x39` | `getClassNumInstanceFields` |
| `0x3A` | `getFieldInClass` |
| `0x76` | `runWithErrorTrap` |

Re-derive it with `hook/tools/jit_slots.py`, which is deterministic and offline-capable
(`--file` takes a local copy):

```powershell
python .\hook\tools\jit_slots.py
```

**The header's answer for this slot is contradicted by the shipped runtime, and the runtime wins.**
Against the real game the probe tried `0x7A` first and got token `0x00000000`; it then tried **`0x76`
and got `0x06001FC5`, which agrees with the token Phase 0 pinned for `frameTick`** — so on this
runtime `0x76` is `getMethodDefFromMethod`, not `runWithErrorTrap`. The header flattening is
therefore off by at least one entry somewhere, or the shipped `clrjit` does not match the generated
header it ships with. **That discrepancy is open and is not worth chasing**: it is recorded because
the design does not depend on resolving it.

This is a *header* result, and the header is not the shipped binary, so it licenses exactly one thing:
**which slots to try**. The hook probes the candidate slots at runtime, in order (`0x7A`, then `0x76`,
then `105`), and accepts the first whose answer is a real `MethodDef` token for a method it has
*already* identified by IL hash — so a wrong index shows up as a wrong number rather than as a silent
misread. Calling a vtable slot with the wrong signature does not fail; it calls an unrelated
function, which is exactly why the runtime probe and not the constant is the authority. The token
itself is diagnostic only; matching is on IL hash (§2.2).

The JIT/EE GUID for .NET 9.0 is `d6218a78-9a34-4c6f-8db5-077a06022fae`
(`jiteeversionguid.h`, `release/9.0`). Like the slot index it is a reference value: the hook reads
the real one out of the loaded `clrjit.dll` and compares.

### 1.2 The four targets, and why no field offset is baked in

Confirmed against the IL dump, all four signatures are favourable — none is generic, none is
tiny enough to be inlined, and the frame tick's only argument is a `float`:

| target | signature | note |
|---|---|---|
| frame tick | `instance void DarzaWindow::Update(float32 total)` | the `float` is `GameTime.TotalGameTime.TotalMilliseconds` — a running total in ms, not a delta. The *increment* between calls (~16.7 ms at 60 Hz) is the liveness signal |
| spawn | `instance void Projectile::ProcessProjectileData(...)` — 16 args | all 16 are on the stack/in registers at entry |
| collision | `instance bool Projectile::HitCharacter()` | `this` is arg 0 |
| escape | `instance void World::RequestEscape()` | no arguments |

The managed-state chain the hook needs for Spike 1.3 is short and all of it is metadata-resolvable:
`World::Shared` (a **static** field of type `World`), `World::Player` (instance, type `Player`),
`Player::Position` (a `GamePoint` value type). The hook reads that chain, and records the offsets it
used on every launch, because a game patch moves them.

### 1.3 Where the offsets come from — and the two-source plan, revised by evidence

[HOOK-ARCHITECTURE.md](HOOK-ARCHITECTURE.md) §5.5 ranks the ways to obtain a field offset and warns
that reading them from the IL in declaration order is a *cross-check only*. The plan was to implement
**two sources and require them to agree**: managed reflection, and `ICorJitInfo::getFieldOffset` from
inside `compileMethod`.

**Phase 1 ships one source and one cross-check, and says so.** Calling `getFieldOffset` means holding a
`CORINFO_FIELD_HANDLE`, and obtaining one from inside the detour requires `getFieldInClass` on the
compiling method's class — which is a *different class* from `World` or `Player`, so it would measure
the layout of whichever type happened to compile first. That is not the check the plan describes, and
a plausible number from the wrong type is worse than an absent one. So:

| source | who computes it | status |
|---|---|---|
| **managed reflection** | the bootstrap, via `Marshal.OffsetOf` and a `ldsflda` dynamic method for the static | **implemented** |
| **a raw pointer chain, compared against reflection** | the bootstrap: read `World.Shared.Player.Position` both ways and require the same coordinates | **implemented** — this is what actually catches a wrong offset |
| **`ICorJitInfo::getFieldOffset`** | the hook, from inside `compileMethod`, on a class handle it can legitimately obtain | **deferred to Phase 2**; reported as a GAP, never as a pass |

The cross-check that replaced it is arguably the stronger test, because it exercises the exact
capability the frame callback depends on. A wrong offset lands on a different object (or a wild one)
and the two routes disagree; the self-check reports check 7 as a failure, the callback is **not**
armed, and the frame detour logs frames with no managed value rather than a plausible wrong one.

## 2. Decisions taken for Phase 1

### 2.1 Injection: launcher with `CREATE_SUSPENDED`, no writes to the game directory

The plan gives two mechanisms ([HOOK-ARCHITECTURE.md](HOOK-ARCHITECTURE.md) §3.1 proxy DLL and §3.2
launcher). **Phase 1 implements §3.2 only**, because §3.1 writes into the game installation and the
`drelay` project's stated principle is that it does not. The launcher:

1. builds a **controlled environment block** from the current environment, then deletes every
   `DOTNET_*` and `DRELAY_HOOK_*` variable and sets exactly the ones it wants — this is the only place
   the `DOTNET_TieredCompilation=1` hazard from §1 of the architecture document can be closed, and it
   removes the whole namespace rather than the one known variable;
2. starts the game `CREATE_SUSPENDED`, so no managed code has run;
3. injects `Drelay.Hook.dll` and calls `DrelayHook_Init` — **in one remote stub**, because
   `CreateRemoteThread` gives the callee one argument and `GetProcAddress` needs two, and because
   `GetExitCodeThread` cannot return a 64-bit pointer. The stub's encoding is in `NativeMethods.cs`
   with the byte layout written out;
4. `ResumeThread`.

`DOTNET_STARTUP_HOOKS` is how the managed bootstrap runs before the game's `Main`. It is set by the
launcher, so the game directory is untouched and both managed DLLs live outside it.

### 2.2 Identity: IL hash is the only thing that decides, the token is a diagnostic

`CORINFO_METHOD_INFO` hands the hook `ILCode` and `ILCodeSize` directly, which is exactly the byte
range Phase 0 hashed (`MethodDef.Rva`, `ILCode[0..ILCodeSize)`, no header, no re-encoding). So the
match is a straight SHA-256 comparison against the table generated from `hook/known-build.json`, and:

- a method whose hash is not in the table is ignored and never patched;
- a **target whose hash is not seen within the discovery window is reported by name** and is not
  patched — "the hook installed but three of four detours never fired" must be distinguishable from
  "the dodge is bad" ([HOOK-ARCHITECTURE.md](HOOK-ARCHITECTURE.md) §9 check 6);
- a build whose assembly hash/MVID does not match makes the hook **refuse to install at all**.

### 2.3 Ordering: the bootstrap waits for the hook, and the hook waits for the bootstrap

Both directions are needed and neither is optional:

- the **bootstrap** runs at the one moment CoreCLR exists and no game code has run, so it is the only
  place the MVID and the field layout can be read from the live runtime;
- the **hook** cannot install its detour until the runtime exists, and must install it *before* the
  game's `Main` compiles anything.

So they rendezvous on named events: the bootstrap publishes its findings, signals, and **blocks**
until the native side confirms the detour is installed. Only then does it return to the host and let
`Main` run. The wait is bounded (30 s) because a hook that hangs the game is a worse failure than a
hook that does not install.

### 2.4 Patching: MinHook, and never inside `compileMethod`

`compileMethod` runs on whichever thread is JITting, and the EE copies the JIT's buffer into
executable memory after the call returns, so the address captured inside the detour is not guaranteed
to be the address that executes (§4.4). Patching there would also mean patching code the JIT is still
finishing. Phase 1 therefore **queues** the address and applies the MinHook patch from the watcher
thread once the process is past startup — one thread, one pass, off the JIT lock.

**Only the frame tick is patched**, and that is a decision rather than an omission: a detour body has
to match the target's calling convention and parameter list exactly, and three of the four targets
have no Phase 1 behaviour to run. Installing a wrongly-shaped forwarder on a per-frame method would
corrupt the game for nothing. The other three are recorded as found-and-verified and reported as
deferred, by name.

The frame detour **calls its trampoline**, so the game's own `Update` still runs. "Observing only"
means observing the real method, not replacing it.

MinHook is vendored under `hook/thirdparty/MinHook` (BSD-2-Clause, `LICENSE.txt` alongside) rather
than referenced as a package: the project has no other native dependency, and a dependency that can
vanish is a worse risk here than the code it saves.

### 2.5 Managed reads happen in a managed callback, not from raw native

[HOOK-ARCHITECTURE.md](HOOK-ARCHITECTURE.md) §5.3 requires this. The bootstrap publishes the address
of an `[UnmanagedCallersOnly(CallConvs = [typeof(CallConvCdecl)])]` method, which is the runtime's
**native-to-managed transition stub** — entering it puts the thread into cooperative GC mode, which is
what makes the reads legal. Publishing a raw managed method address instead would run managed code in
preemptive mode, which is how a native hook corrupts a GC. The native side never walks a managed
object graph on its own.

**There are two such callbacks, and the split is load-bearing.** `OnFrame` runs on the game's thread
inside the frame detour and reads one float; it must not allocate, block or throw. `OnProbe` runs on
the native watcher thread and answers *"is there a world yet, and do the measured offsets describe
it?"* — which needs reflection, so it is deliberately not on the frame path. The watcher calls the
probe at every wait it does, and the probe opens the gate `OnFrame` reads through. This is what makes
Spike 1.3's read happen at all: the gate used to be decided at attach, where `World.Shared` is always
null, so the callback was disabled for every session and the read never ran. See
[PHASE1-HANDOFF.md](PHASE1-HANDOFF.md) §12 for the design and the two tests that cover it.

### 2.6 The off switch is honoured before any patch

`--off` on the launcher. "Off" means the process is untouched: the startup hook is not installed at
all, and the native side writes one line and installs nothing. It is checked before the JIT detour is
written, not after.

## 3. What each spike's evidence is

Everything Phase 1 produces lands in a **run directory**
(`%LOCALAPPDATA%\drelay\hook\<timestamp>-p<pid>`), so a session is one folder rather than five files
in five places:

| file | written by | proves |
|---|---|---|
| `hook.log` | native + bootstrap | Spike 1.1: the bootstrap's first line, and where it sits relative to the game's own log |
| `selfcheck.txt` | native | the §9 acceptance test, one line per check, PASS / FAIL / GAP |
| `sizeof.txt` | the build | the compiler's own view of the shared layout, diffed against the generator's |
| `events.jsonl`, `summary.txt` | native | the shared block drained at exit: targets, offsets, frame counts, self-check |

There is no `trace.csv` / `targets.csv`: the trace and frame rings live in the shared block and are
drained at exit as `events.jsonl` and `frames.csv`, which avoids file handles in the game's frame path
and keeps the evidence in one place. A ring that overflowed says so rather than looking complete. The
whole-run size record (`hook.log.sizes`) and the near-miss table (`hook.log.observed`) are written by
the flusher thread, not by the JIT thread, for the same reason.

**Spike 1.1's success test is a comparison**, not the existence of a line: the bootstrap line must be
earlier than the game's own first log line, and the MVID it reports must equal `hook/known-build.json`'s.
The launcher prints both at exit.

**Spike 1.2's success test is that all four targets are matched by IL hash and that their native
addresses are stable across two runs** — the stability is what proves `TieredCompilation: false` is in
effect, which is the single assumption the whole design rests on. All four are now matched; the
cross-run address comparison is done by diffing the `targets` block of `events.jsonl`.

**Spike 1.3's success test is plausible live values at 60 Hz, and only its first half has been met.**
The frame detour's argument is `GameTime.TotalGameTime.TotalMilliseconds`, so the evidence is the
*increment* between calls — ~16.7 ms at the design 60 Hz — which the detour logs at call 120 and
which `frames.csv` records per row as `frame_delta_ms`. That half works: the loop is periodic and the
detour is on the real method.

**The second half is the managed read, and its blocker is gone.** It used to be gated on an offset
cross-check attempted only at attach, when `World.Shared` is still null — so the gate closed, the
callback was disabled for the session, and the read never ran. The gate is now opened by a probe the
watcher thread runs once a world exists (§2.5), and both outcomes are covered by runs 5 and 6 of
`hook/tools/Test-Injection.ps1`. What remains is a live session in which the *game's* world appears and a
real frame tick reaches the callback; see §6.2 and PHASE1-HANDOFF.md §12.

## 4. What Phase 1 deliberately does not do

- **No dodge, no trajectory model, no nexus decision.** Phase 1 reads; it does not decide.
- **No bridge.** [JAVA-BRIDGE.md](../bridge/JAVA-BRIDGE.md) is Phase 4, and its own rule is that the hook must
  never block on the relay. Nothing in Phase 1 depends on the relay, so "killing the relay changes
  nothing" is true by construction — and is still on the live checklist.
- **No writes to game memory other than the detours themselves.** No position writes, no field
  writes: the sole write is the trampoline patch at one target, which is the mechanism, not a side
  effect.
- **No writes to the game directory.** Enforced by the launcher design, not by convention.

## 5. Findings from building it

Four of these cost real debugging time and are recorded so the next reader does not repeat them. Two
are in the layout generator, which is the part of Phase 1 most likely to be "simplified" later.

**1. Hand-writing the shared-block offsets produced three wrong answers at once.** A first attempt
stated `[FieldOffset]` values by hand for the managed view of `DrelayShared`, and every one of them
was wrong — including the two that the arithmetic made look obvious, because the structs' own
alignment and the ring sizes are not guessable from their field lists. The layout is now
**generated** from the native header by `hook/tools/gen_shared_layout.py`, and the model is checked
against the compiler by `native/SizeProbe.c`, which `build.ps1` compiles and runs and diffs. The
generator's model was itself wrong twice — it aligned embedded structs to 8 instead of their own
alignment, and it aligned arrays to their total size instead of their element type — and both times
the compiled probe is what said so.

**Do not quote the layout sizes from memory, and treat any number written into a comment or a
document as stale until the probe confirms it.** The values the code was first built against were
replaced twice by struct changes, and prose kept repeating the old ones. The current measured
values come from `build.ps1`'s own probe output:

```
DrelayTargetHash 104      DrelayFieldOffset 84      DrelayShared 440912
DRELAY_SHARED_SIZE 440912
```

`DRELAY_SHARED_SIZE` is pinned by a `static_assert` in the header, so a future drift fails the
build rather than being discovered by a run.

**2. A vtable slot index derived from the runtime's own generated header was still not the index the
shipped runtime uses.** §1.1. The header flattening puts `getMethodDefFromMethod` at `0x7A` and
`runWithErrorTrap` at `0x76`; the live probe gets token `0` from `0x7A` and the correct token from
`0x76`. Calling a vtable slot with the wrong signature does not fail — it calls an unrelated
function — so the slot is chosen at runtime by testing candidates against tokens Phase 0 already
knew, and the header is used only to decide *which* candidates to try.

**3. A batch file does not continue a command across a line break, and `cl.exe` with no input file
waits on stdin.** The build script's first version wrote the compiler command across several lines;
`cmd` executed `cl.exe` alone and the argument list became a stray redirect. The build then *hung*
rather than failing, because cl reads stdin when it has no input file. Every invocation is now one
physical line with `< nul` on it. This is in the script as a comment because the symptom is a hung
build, which reads as "the compiler is slow" rather than "the command was malformed".

**4. A `#define` parser that lets the identifier and the value run together silently drops names.**
`#define\s+(DRELAY_\w+)\s+([0-9]+)` matched `DRELAY_MAX_STEPS 8` and skipped
`DRELAY_MAX_TARGETS 8`, because with no separator required the regex engine can split the name at the
last underscore and read the tail as the beginning of the value. The identifier is now
`[A-Za-z_][A-Za-z0-9_]*` with mandatory whitespace before the value, and the managed side takes every
constant the header defines rather than a hand-listed subset.

## 6. Verified, and not verified

### 6.0 The offline injection test

`hook/tools/Test-Injection.ps1` runs the whole launcher → injection → bootstrap → native chain
against a synthetic self-contained .NET host staged from the game's own runtime, so that everything
except the game's *assembly* can be exercised without an operator. **It passes 73 of 73 checks.**
What it proved on the way is worth more than the pass, because none of it was visible by reading the
code:

| found | the fix, and what the symptom was |
|---|---|
| the shared block could not be created at all | a 1.9 MB named pagefile section fails `CreateFileMapping` with error 8 while gigabytes are free. The block is now file-backed in the run directory, which has no commit charge. `tests/MapProbe` is the measurement |
| the host could not find CoreCLR | staging ten DLLs is not a self-contained deployment. The test now stages the whole runtime and derives the host's `deps.json` from the game's |
| the bootstrap never ran | the type must be named exactly `StartupHook` in the **global** namespace; `Drelay.Bootstrap.StartupHook` gives `TypeLoadException: Could not load type 'StartupHook'` |
| the native log was always empty | the flusher's first pass opened the file `"wb"` and truncated the bootstrap's lines. It now always appends, the two writers have separate files, and every watcher exit path flushes synchronously |
| the native side crashed reading the JIT/EE GUID | `getVersionIdentifier` was called with a by-value 16-byte return type where the runtime declares `void getVersionIdentifier(GUID*)`. **Fixed** — see §6.1 item 3 |

The three checks added in the most recent round assert the two instruments that decide how a run is
read: that the run records which process it is (pid, image, foreground owner), and that it accounts
for every entry into the detour rather than only the ones it inspected.

### 6.1 The investigation log — concluded

Both blockers are fixed and Phase 1's chain works against the real game. This section is kept
because the *eliminations* are the reusable part: [PHASE1-HANDOFF.md](PHASE1-HANDOFF.md) carries the
conclusions and the current state, this carries the evidence for how each conclusion was reached.

#### 1. A startup hook cannot JIT-compile anything

The first blocker. `RuntimeHelpers.PrepareMethod` crashed with the same fatal CLR error it was
supposed to help diagnose, naming itself:

```
Fatal error. Internal CLR error. (0x80131506)
   at System.Runtime.CompilerServices.RuntimeHelpers.PrepareMethod(System.RuntimeMethodHandle, ...)
   at Drelay.Bootstrap.HookEntry.Run()
   at Drelay.Bootstrap.HookEntry.Initialize()
```

**A startup hook runs before method compilation is fully wired up. Any call that forces a method to
be compiled for the first time faults the process, and the stack always names the startup hook
rather than the compiler.** That one sentence explains every apparently unrelated crash across five
rounds:

| crash | why it is the same bug |
|---|---|
| `RuntimeHelpers.PrepareMethod` | it compiles, by definition |
| `ThreadPool.QueueUserWorkItem` | starting the pool JIT-compiles the pool's own machinery |
| `new Thread(...).Start()` | starting a thread runs a *new* method body for the first time — a compilation |
| a blocking `WaitForSingleObject` | the first P/Invoke marshalling stub in the process is JIT-compiled |
| the `compileMethod` detour, MinHook, the frame-callback address | **all red herrings.** None was ever the cause |

**The redesign that follows from it, and it works.** The bootstrap is reduced to what it can
actually do — **marshal bytes, set an event, return** — and everything that needs compiling moves
behind a **resolve callback** that the *native* side invokes once the runtime is up.
`ManagedFrameCallback.OnResolve` is an `[UnmanagedCallersOnly]` stub; taking its address emits no
code, so publishing it from the startup hook is safe, and the native side calls it from its own
thread after installing the detour.

#### 2. A blocking `WaitForSingleObject` cannot be used from the injected thread

A zero-timeout probe proved the event handle valid, so the fault was the *blocking* form of the call
rather than the object. Replacing it with a poll loop — a zero-timeout wait plus `Sleep(5)` —
removed the fault entirely, and `native ready: yes` / `jitDetoured` / `6 passed / 0 failed`
followed.

**What the workaround costs, stated plainly.** Phase 1's ordering guarantee was "the detour is
installed before the game's first frame". The bootstrap now signals before the native side installs,
and the native side polls rather than being woken. Neither changes the *mechanism* — the detour is
still installed within ~100 ms of startup, long before any projectile spawns — but the guarantee is
weaker than the one the plan wrote down, and it is weaker because of a platform behaviour that is
not understood rather than because of a design choice.

**The unresolved question, worth one experiment later.** *Why* a native thread created from an
injected DLL can perform a zero-timeout wait on an event but not a blocking one is not known. It is
not the CLR (the thread predates it) and it is not the handle (the probe proved it valid). The
likeliest explanation left is that the runtime's startup thread enumeration suspends and resumes
this one into a state it cannot handle. That is a hypothesis, not a finding, and it is recorded as
such.

#### 3. The crash that was not the detour — an ABI error in `getVersionIdentifier`

For several rounds the process died with `Fatal error. Internal CLR error. (0x80131506)` while the
`compileMethod` detour was installed, and the eliminations all pointed at the detour's mere
presence. Every one of them was downstream of the actual fault, which happened **inside
`DrelayRuntimeValidate`, before the detour existed**:

| ruled out (correctly, but too late in the sequence) | how |
|---|---|
| the launcher and the injection stub | off mode exits cleanly, with the same stub, the same environment block and the same remote thread |
| the bootstrap and managed state | the host runs clean with the bootstrap loaded and **no** native DLL |
| target patching and MinHook's thread suspension | the no-patch control installs the detour and patches nothing; the crash persisted |
| per-compilation CryptoAPI in the JIT callback | the IL-size pre-filter runs **before** any hashing, so a size-less run does no crypto work at all |
| `thread_local` in a runtime-loaded DLL | replaced with an own-slot `TlsAlloc`, allocated before the detour exists |
| the `__try`/`__except` frame in the detour | removed; the body cannot fault on what it reads |
| anything the detour *does* | the forward-only control reduces it to a pure forwarder — no shared-block read, no hash, no log, no counter — and the crash persisted |

**The real cause.** `getVersionIdentifier` was declared with a *by-value* 16-byte return type; the
runtime's own header (`src/coreclr/inc/corjit.h` at `release/9.0`) declares
`void getVersionIdentifier(GUID*)`. A by-value aggregate makes MSVC pass a hidden return pointer in
`RCX`, pushing the real arguments along by one register, so the callee received `&returnBuffer`
where it expected `this` and wrote 16 bytes of GUID straight into `clrjit!g_CILJit`. Everything
after that was a process holding a JIT object whose first eight bytes were no longer a vtable.

The proof was a symbol lookup rather than an argument: `coreclr.dll` and `clrjit.dll` PDBs from the
Microsoft symbol server resolved the two fault addresses to `UnsafeJitFunction+0x59D` (inline
`invokeCompileMethodHelper+0x6E`, `mov rax,[rax]` — loading `m_jit->vtable[0]`) and
`CEEInfo::JitProcessShutdownWork+0x26` (`mov rax,[rax+8]` — `m_jit->vtable[1]`). Both faults were
literally the vtable-slot load, both `read of 0xFFFFFFFFFFFFFFFF`.

**Why no control found it.** Every skip switch was downstream of `DrelayRuntimeValidate`, and the
corruption happens inside it. The one control that removed the corrupting call removed the entire
watcher with it, so it looked like a coarse answer rather than the answer. **§8's three questions
need a fourth: is the step you suspect *inside* the range your control covers?**

#### 4. The targets never compiled — a leaked re-entrancy counter

Five live runs with the operator demonstrably inside a realm reported `0 of 4 targets matched`, and
the per-target verdict said `frameTick IL size 1286: ZERO compiled`. The frame tick runs once per
frame, so this was read as a statement about the game — first as an operator-coverage problem, then
as a process-identity problem. Both readings were wrong, and the second one was argued from a flat
compilation count rather than measured; the game's own log (`darza.log`) shows the hooked pid
entering `GameScene` and connecting to a server in the very run that reported `ZERO compiled`.

The cause was one line of arithmetic. `HookCompileMethod`'s re-entrancy guard called
`EnterDetour()`, which incremented a per-thread TLS depth **unconditionally** and returned the
*previous* value; the "re-entered, skip" path returned without the matching `LeaveDetour()`. The
depth therefore never came back to zero, and **every later compilation on that thread was silently
discarded** — not counted, not hashed, not size-matched, not in the size histogram.

**The instrument lesson, and it is the one that cost the most.** Two instruments appeared to confirm
`ZERO compiled` independently — a size histogram and an `OnCompiled` IL-hash comparison — and both
sat *downstream of the same guard*. Two instruments that share a code path are one instrument. An
instrument can only be trusted to the extent its own blind spot is measured, which is why
`g_detourInvocations` is now counted **before** the guard.

Two further instrument defects were found while fixing this, both of which had been reporting
confidently:

- **the histogram was lossy and was the instrument of record.** 512 slots keyed by `size % 512` with
  a **64-probe cap**, documented as "far more than a session produces (a few hundred at most)". A
  real session exceeded it: one run filled all 512 slots and dropped 61 compilations, the run before
  it dropped 101. The per-target verdict was derived from that table. It did not in fact produce a
  wrong answer — the probe chain from each target's slot reached a free slot well inside the cap,
  which is why the earlier finding survived and was verified by
  `hook/tools/analyze_size_histogram.py` — but a verdict that *can* be produced by an instrument fault is
  worse than no verdict. The table is now 4096 slots, the probe covers all of it, and the per-target
  count is a direct size comparison that uses no table at all;
- **three operator switches were unreachable.** The launcher deletes every environment variable
  beginning with `DRELAY_HOOK_`, so `DRELAY_HOOK_NO_PATCH`, `DRELAY_HOOK_FORWARD_ONLY` and
  `DRELAY_HOOK_NO_FRAME_CB` could never be set through the only supported way to start the game.
  They are `DRELAY_NO_PATCH`, `DRELAY_FORWARD_ONLY` and `DRELAY_NO_FRAME_CB`. The first of these had
  already produced a false elimination in item 3 above: a control set from the operator's shell
  silently did nothing, and the run was read as "the control was engaged and the fault persisted".
  (`DRELAY_NO_FRAME_CB` has since been **removed**: there is no managed frame callback to suppress —
  see PHASE1-HANDOFF.md §13. `DRELAY_NO_PATCH` and `DRELAY_FORWARD_ONLY` remain.)

#### 5. The patch crashed the game — the frame-tick detour dropped `this`

The first run that found a target patched it and died on the first frame. The crash report named it
precisely: an `ACCESS_VIOLATION` at `nativeEntry + 0xB7`, reading address `0x3F`, reproduced at the
identical offset in a second run on a different build and a different pid.

`DarzaWindow.Update` is an **instance** method — `this` in `RCX`, `total` in `XMM0` — and the detour
and its trampoline were declared `void(float)`. The trampoline *is* the method's own prologue
followed by a jump back into its body, so the body ran with whatever `RCX` the detour left behind. A
fixed fault offset and a fixed bogus base of zero is a deterministic wrong `this`, not a torn
instruction. Carrying the receiver explicitly through the detour and the trampoline fixed it:
**999–1002 frames entered, 14 µs worst call, no crash.**

**This is the third ABI-shape fault in the phase** (the other two are in item 3 and in
`CORINFO_METHOD_INFO`, whose `ftn`/`args` order and 96-byte `CORINFO_SIG_INFO` put `ILCode` at 104
instead of 16). When a hook faults, read the fault offset relative to the patched entry before
reading anything else, and treat any signature written from documentation rather than from the
callee's declaration as unverified.

#### 6. Two instrument bugs that were telling a different story than the one intended

- **`frames.csv` was headed `arg_total_s,implied_hz`** and printed `1/arg` as a frequency. The
  argument is `GameTime.TotalGameTime.TotalMilliseconds` — a monotonically increasing *total in
  milliseconds* — so as seconds it read as an absurd 27,824-second frame at 0.00 Hz. It now reports
  `arg_total_ms` and the derived `frame_delta_ms`, which is what actually proves the detour is on a
  periodic frame loop (~4.9 ms uncapped at the title screen).
- **`target-size` printed `compiled N time(s) but did not match` about a target it had just matched
  and patched.** That wording was accurate only while no target had ever matched.

#### 7. A bug worth remembering, about every diagnostic in this project

The native log was being lost entirely on a hard process kill: `fclose` flushes stdio, but the
process never reached it and the 250 ms flusher thread never got its turn. Rounds of investigation
were run against an empty log as a result. `DrLogFlushNow` now fires immediately after each decisive
line, `fflush` precedes `fclose`, and the discovery-window close flushes too. **A diagnostic that
only survives success is not a diagnostic.**

#### 8. The method note

Every wrong conclusion in this phase came from a control or an instrument that was not verified to
be doing what it claimed. The questions to ask of any control:

1. **Did it run?**
2. **Did it change what it claimed to change?**
3. **Would the log have said so if it had not?**
4. **Is the step you suspect inside the range your control covers — and does the instrument share a
   code path with the thing it is measuring?**

The habit that actually works, and it is what found both root causes in one round each after five
rounds of elimination had failed on the first: **a flushed checkpoint after every single step, plus
a switch that removes exactly one step.** Build the instrumentation before the hypothesis, not after
it.

And the habit that would have saved the most time here: **the game's own log is ground truth.**
`%LOCALAPPDATA%\RippleStudio\Darza\logs\darza.log` is timestamped, names the scene and the focus
owner, and would have answered "which process played, and how far did it get" in one file read. A
round was spent arguing the opposite.

#### 9. Instrumentation the later rounds added, and how to read it

| instrument | where | why it exists |
|---|---|---|
| `detour accounting` | `hook.log`, `summary.txt` | counts detour entries **before** the re-entrancy guard, so "the hook was not looking" can never again be reported as "the game never compiled it" |
| exact per-target size counters | `hook.log` (`target-size`), `summary.txt` | a verdict that cannot be produced by an instrument fault; four comparisons, no hashing, no eviction |
| `hook.log.sizes` | run directory | every distinct IL size in the run with its count — the whole-stream record the ring cannot give |
| `hook.log.observed` | run directory | up to 16 distinct hashes whose size matched a target but whose hash did not, surviving ring eviction |
| `crash.txt` | run directory | a vectored exception handler writing exception code, faulting address resolved to `module+0xRVA`, a stack walk and a raw stack scan. **`AddVectoredExceptionHandler(1, …)` inserts at the HEAD, so handlers registered with `First=1` run in REVERSE registration order** — this DLL registers before CoreCLR exists, so the runtime's own handler ran first and consumed the fault until `DrelayArmCrashReporter` re-registered at each new decision point. A module list snapshotted at injection time contains no runtime modules; it is taken again from the watcher thread |
| `process identity` | `hook.log` | own pid and image, a census of same-named processes with parent pids, and the foreground window's owner sampled across the discovery window — so "the operator was playing somewhere else" is measured, not argued |
| `hook/tools/analyze_size_histogram.py` | `tools/` | replays the probe-chain argument against a saved `hook.log.sizes` and says, per target, whether its absence is **proven** or **unfalsifiable** |

**Known gaps, reported as gaps rather than passes:**

- **The bootstrap targets `net8.0`, not `net9.0`.** The only SDK here is 8.0.202, which refuses
  `net9.0` (NETSDK1045). It does not matter for a startup hook — the host is already running .NET 9
  and the bootstrap uses no .NET 9 API — but it is a guarantee given up, and the failure mode is
  caught loudly (the native side times out and says so).
- **In-process MVID is checked by the native side reading the file**, not by asking the runtime for
  the loaded image. It catches a wrong build; it would not catch a loaded image that differs from
  the file on disk.
- **The `ICorJitInfo::getFieldOffset` cross-check is Phase 2's**, as §1.3 explains.
- **The relay bridge is Phase 4 and absent.**
